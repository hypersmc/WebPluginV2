# WebPlugin 4.2B — PHP environment bridge and recurring schedules

Both features extend WebPlugin's existing modular PHP runtime and `DeploymentTasks` supervisor. They are **opt-in** and work across Bukkit/Paper, BungeeCord and Velocity. No external cron daemon, shell, SSH or PHP system binary is required on the Minecraft host.

## 1. Environment variables for PHP-FPM and CLI

```yaml
Environment:
  Enabled: true
  InheritContainerEnvironment: false
  FromContainer: [APP_ENV]  # only explicitly named existing container values
  Variables:
    APP_DEBUG: "false"
    APP_TIMEZONE: Europe/Copenhagen
  SecretsFile: "production.env"
```

`SecretsFile` resolves **only** under `plugins/webplugin/private/`. For example `plugins/webplugin/private/production.env`:

```dotenv
# Private PHP configuration; not an HTTP-served Laravel .env file
DB_HOST=database
DB_PASSWORD=my-long-secret
APP_KEY=base64:replace-with-actual-app-key
```

- Variable precedence: explicit `FromContainer` allowlist, then `Variables`, then `SecretsFile` (later entries win). Missing required container variables cause a configuration error rather than silently injecting empty values.
- The secrets file supports a minimal literal `KEY=value` format and `#` comments, **not** shell execution, quotes removal, interpolation, multiline values or Laravel dotenv syntax. File permissions should be limited to the Minecraft server's own account (e.g. 0600 where supported). Do not put secrets into version-controlled `config.yml` or the public document root.
- When enabled and `InheritContainerEnvironment: false`, PHP subprocesses get only the configured keys, essential `PATH`/`LANG` settings and WebPlugin's native `LD_LIBRARY_PATH`. `LD_*`, `PHPRC`, `PHP_INI_SCAN_DIR` and related process-control keys cannot be injected.
- For PHP-FPM, WebPlugin updates the existing `www.conf` pool with **names only**:
  ```ini
  ; BEGIN WEBPLUGIN MANAGED ENVIRONMENT
  clear_env = yes
  env[DB_PASSWORD] = $DB_PASSWORD
  env[APP_DEBUG] = $APP_DEBUG
  ; END WEBPLUGIN MANAGED ENVIRONMENT
  ```
  The real values are in the FPM master process environment and forwarded explicitly to worker processes. The managed block is idempotent and is removed when `Environment.Enabled` is later set to false and the plugin restarts.
- The same selected variables reach bundled PHP CLI deployment tasks and scheduled tasks. They are **not** forwarded to NGINX; the PHP preflight check does not need secrets.
- The built-in bridge does **not** edit a framework's existing `.env`. Environment variables can still be read by PHP code via `getenv()`; a compromised PHP application can exfiltrate what it is allowed to use. Landlock filesystem restrictions are a separate security control.
- Restart WebPlugin after changing environment config or its private file. Do not use `phpinfo()` or `var_dump($_ENV)` on a publicly reachable page to test secrets. At present the administrator command `/webptasks environment` (or Bukkit `/webp tasks environment`) returns only enabled status and a count, never secret values.

## 2. Built-in cron and interval runner

No new supervisor is created: recurring tasks enter the existing bounded, asynchronous process supervisor and use the same bundled PHP, configured environment and Landlock task profile.

A normal Laravel recurring scheduler:

```yaml
DeploymentTasks:
  Enabled: true
  MaxProcesses: 8
  Tasks:
    - Id: laravel-schedule
      Type: scheduled
      Runtime: bundled-php
      WorkingDirectory: websites/laravel
      Arguments: [artisan, "schedule:run"]
      Schedule: "* * * * *"
      TimeZone: Europe/Copenhagen
      OverlapPolicy: skip
      AutoStart: true
      TimeoutSeconds: 50
      SuccessCodes: [0]
```

Or replace `Schedule` with an interval like `Every: 6h` (use **one**, not both). Intervals require a unit `s`, `m`, `h` or `d`, from 10 seconds through 365 days. `TimeZone` uses Java's IANA zone names; default is UTC.

Five-field cron syntax is `minute hour day-of-month month day-of-week`. Supported expressions include `*`, `*/N`, numbers, ranges, and comma-separated items. Weekday 0 or 7 is Sunday. If both day-of-month and day-of-week are restricted, the standard cron **OR** rule is used. Named months/days, `@daily`, L/W/# macros and seconds-as-a-sixth-field are not supported.

Every cron minute or interval is considered **at most once**, and only while the plugin/server is running. If another instance of that task is still running or process capacity is full, the occurrence is skipped (never backlogged, never spawned in parallel). No missed jobs are replayed after downtime; interval counting starts on initialization. This design prevents unbounded execution in small Pterodactyl containers.

For administration:
- Bukkit/Paper: `/webp tasks list`, `/webp tasks status`, `/webp tasks stop laravel-schedule`, `/webp tasks start laravel-schedule`, `/webp tasks run laravel-schedule`.
- Bungee/Velocity: corresponding `/webptasks ...` commands.
- **stop** pauses future schedule occurrences and stops an active process. **start** resumes future schedule occurrences without immediate backfill. **run** triggers a single immediate execution without changing the automatic schedule.
- Command permissions follow the existing task administrator permission (`web.tasks` on Bukkit, `webplugin.tasks` on proxies). Recurring task arguments are only read from trusted server configuration; player chat never becomes a shell command.

If all you need is Laravel's persistent scheduler, `php artisan schedule:work` is still supported as a normal `service` task. Do **not** run both `schedule:work` and a recurring `schedule:run` for the same application.

## Beta validation and limitations

CI covers the environment key allowlist, private secrets-file handling, generated PHP-FPM pool references (without cleartext values), five-field cron parsing and timezone/DST-relevant calendar handling, bounded interval input, and an actual recurring job on the existing supervisor.

A real Pterodactyl PHP-FPM worker still needs to be tested with harmless environment variables (e.g. `APP_ENV`) before relying on the bridge for production application credentials. PHP profile hardening, per-site isolation, secrets rotation without server restart, deployment ordering and additional scheduler policies remain future work in PR #5. Existing 4.1R config files may need the new sections manually added; both features remain off by default.
