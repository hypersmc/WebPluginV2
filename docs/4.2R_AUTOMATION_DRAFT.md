# WebPlugin 4.2R — Automation & Landlock development foundation

**Status: prototype; NOT wired into the Bukkit, BungeeCord or Velocity plugin lifecycles yet.**

This package supplies reusable Java components and the provided ServerFabric-style C Landlock launcher. It deliberately does not replace the released 4.1R source, modify the GitHub runtime repo, or alter PHP/NGINX startup behavior.

## Core components

- `ProcessSupervisor`: multiple independent one-shot/service OS processes, limited concurrency, bounded output, asynchronous monitoring, timeout handling, service restarts with exponential backoff and a 10-failure circuit breaker, graceful stop and forced cleanup.
- `TaskDefinition`: validated, configuration-driven `bundled-php` invocation with separate arguments; modes `once`, `once-per-deployment`, `every-start`, `manual`; services allow `Instances` and `Restart`.
- `TaskEngine`: starts eligible jobs and services without waiting for long-running processes; delegates PHP launcher construction to the existing modular PHP runtime layer.
- `TaskLedger`: atomic persistence of successful one-shot job completion separate from config. No literal removal of a task after completion.
- `LandlockSandbox`: optional WebPlugin-wide security manager for PHP-FPM, NGINX and tasks. Runs a native helper `--probe` once; `preferred` can run unsandboxed when support is absent; `required` blocks affected launches. A helper failure after a successful probe is not retried unsandboxed.
- `native/webplugin-landlock.c`: the C helper supplied from ServerFabric; compiles on Linux with the required kernel headers.

## Example 4.2R configuration (planned integration)

```yaml
Security:
  Landlock:
    Enabled: false              # strongly recommended after installing helper
    Mode: preferred             # preferred | required
    HelperPath: ""              # default: plugins/webplugin/bin/webplugin-landlock

DeploymentTasks:
  Enabled: false
  MaxProcesses: 8
  Tasks:
    - Id: laravel-install
      Type: oneshot
      Runtime: bundled-php
      WorkingDirectory: websites/myapp
      Arguments: [artisan, migrate, --force, --no-interaction]
      Run: once-per-deployment
      DeploymentId: release-1
      SuccessCodes: [0]
      TimeoutSeconds: 180
      Restart: never
    - Id: laravel-queue
      Type: service
      Runtime: bundled-php
      WorkingDirectory: websites/myapp
      Arguments: [artisan, queue:work, --sleep=3, --tries=3]
      Instances: 2
      AutoStart: true
      Restart: on-failure
      TimeoutSeconds: 0
      SuccessCodes: [0]
    - Id: laravel-scheduler
      Type: service
      Runtime: bundled-php
      WorkingDirectory: websites/myapp
      Arguments: [artisan, schedule:work]
      Instances: 1
      AutoStart: true
      Restart: on-failure
      TimeoutSeconds: 0
      SuccessCodes: [0]
```

## What still needs integration

1. Add adapter calls in all three plugin startup/shutdown paths, and expose task admin commands with platform permissions.
2. Add `LinuxPhpProcessRunner.createPhpCliBuilder(...)` reusing generated php.ini and bundled glibc/lib paths; do not construct `php` using PATH.
3. Apply `LandlockSandbox.protect` to NGINX and PHP-FPM processes **as well as** TaskEngine commands; validate on actual Pterodactyl eggs.
4. Compile the native C launcher for supported Linux architectures, distribute it through a versioned, checksum-verified runtime archive. Do not compile C or apt-install packages inside the Minecraft container.
5. Add explicit per-site path profiles, configuration migration, strict admin-only task controls, task health checks, and integration tests. Confirm the site can reach database sockets and valid system certificate stores.
6. Add deployment gating (`OnFailure: block-web`) only after the lifecycle/adapters support per-site readiness without stopping Minecraft.

## Security boundaries

- `ProcessBuilder` avoids shell token interpretation but is **not** a sandbox. The configured PHP scripts execute with the Minecraft process's Unix user and may access its resources if Landlock is disabled/unavailable.
- The example default filesystem rules prioritize compatibility, not full process/network isolation. Landlock is not a container; it does not by itself isolate TCP destinations, environment secrets, or existing inherited file descriptors.
- If a website root or task working directory is `/home/container`, isolation of Minecraft files is ineffective. Reject or prominently warn when the configuration grants the whole server root.
- Trusted server administrators must own the task configuration. Never expose arbitrary task arguments or a shell command executor to HTTP requests or unauthenticated users.
- `once` is **at-least-once with best-effort deduplication**, not a transactional exactly-once guarantee. Keep tasks idempotent, and use Laravel's migration tracking.
- `php artisan key:generate` must never be a recurring task: regenerating the application key may make existing encrypted data inaccessible.

## Local smoke tests

```bash
mkdir -p /tmp/webplugin-automation-classes
javac -d /tmp/webplugin-automation-classes \
  src/main/java/me/jumpwatch/webserver/automation/*.java \
  src/test/java/me/jumpwatch/webserver/automation/*.java
java -cp /tmp/webplugin-automation-classes me.jumpwatch.webserver.automation.ProcessSupervisorSmokeTest
java -cp /tmp/webplugin-automation-classes me.jumpwatch.webserver.automation.TaskEngineSmokeTest
cc -Wall -Wextra -O2 native/webplugin-landlock.c -o /tmp/webplugin-landlock
/tmp/webplugin-landlock --probe
```

Test commands use `sh` **only inside the dedicated test classes**, never as an API offered by the production task engine.
