# WebPlugin 4.2B — Automation & Landlock beta development

**Status: integrated beta code on the draft PR; not yet validated on production Minecraft/Pterodactyl servers.**

This PR contains the shared automation classes, integration into Bukkit/Paper, BungeeCord and Velocity, and the ServerFabric-style C Landlock helper source. The released 4.1R master branch and runtime download repository are unchanged.

## Core components

- `ProcessSupervisor`: multiple independent one-shot/service OS processes, limited concurrency, bounded output, asynchronous monitoring, timeout handling, service restarts with exponential backoff and a 10-failure circuit breaker, graceful stop and forced cleanup.
- `TaskDefinition`: validated, configuration-driven `bundled-php` invocation with separate arguments; modes `once`, `once-per-deployment`, `every-start`, `manual`; services allow `Instances` and `Restart`.
- `TaskEngine`: starts eligible jobs and services without waiting for long-running processes; delegates PHP launcher construction to the existing modular PHP runtime layer.
- `TaskLedger`: atomic persistence of successful one-shot job completion separate from config. No literal removal of a task after completion.
- `LandlockSandbox`: optional WebPlugin-wide security manager for PHP-FPM, NGINX and tasks. Runs a native helper `--probe` once; `preferred` can run unsandboxed when support is absent; `required` blocks affected launches. A helper failure after a successful probe is not retried unsandboxed.
- `native/webplugin-landlock.c`: the C helper supplied from ServerFabric; compiles on Linux with the required kernel headers.

## Integrated in the 4.2B branch

- On boot, Bukkit, BungeeCord and Velocity construct a shared `WebPluginAutomation` manager, probe the native Landlock helper and start enabled PHP CLI jobs after the PHP runtime has been installed.
- The three platform-specific PHP startup classes use the same protected `LinuxPhpProcessRunner`; Landlock wraps PHP-FPM, NGINX and the PHP CLI preflight. The Minecraft JVM is not sandboxed.
- The PHP command factory uses the bundled PHP binary, generated php.ini, enabled extension packs and glibc loader. No system-PHP or shell fallback.
- Admin commands: `/webp tasks list|status|logs|start|stop` and `/webp sandbox` on Bukkit; `/webptasks list|status|logs|start|stop|sandbox` on BungeeCord and Velocity. Permission: `web.tasks` (Bukkit) or `webplugin.tasks` (proxies).
- When `Settings.EnableHTML: false`, the Java HTML socket does not bind `HTMLPORT`. NGINX/PHP is independent of that setting.

## Remaining beta work and validation

1. Verify the full Maven build for all three platform APIs, real process startup, Laravel integration and failure handling. GitHub Actions checks are configured in `.github/workflows/4.2b-automation.yml`.
2. The CI workflow publishes a beta artifact containing `WebPlugin-4.2B.jar` and a **statically linked Linux x86-64** `webplugin-landlock` binary. Upload the binary to `plugins/webplugin/bin/webplugin-landlock` (or set `Security.Landlock.HelperPath`) and make it executable. Other architectures need a separate helper build. No compiler is required inside Pterodactyl.
3. Ensure `Landlock: AVAILABLE` appears in startup logs before testing `Enabled: true`; on unsupported containers, `preferred` logs its unsandboxed fallback and `required` refuses the affected launches.
4. Add controlled dependency ordering between one-shot setup tasks and queue workers. **This beta starts eligible jobs concurrently; do not depend on migrations finishing before queue workers unless migrations are manually triggered first.**
5. Validate compatibility filesystem rules, system CA bundles, DNS, DB connections, NGINX logs and PHP-FPM temp paths against real websites.
6. Add durable deployment gating (e.g. `OnFailure: block-web`) only when site lifecycle/readiness can support it without stopping Minecraft.

### Configuration upgrade

Existing 4.1R config files may not automatically gain new commented sections. Add `Security.Landlock` and `DeploymentTasks` from `src/main/resources/config.yml` manually. Both new features are off by default, so existing hosting behavior remains unchanged until enabled. `Settings.EnableHTML` now correctly controls the standalone Java HTML listener.

### Testing the 4.2B beta from the PR

1. Open PR #5's most recent green **WebPlugin 4.2B automation checks** workflow run and download the `WebPlugin-4.2B-linux-amd64` artifact.
2. Use the JAR only on a disposable test Minecraft server. Save your 4.1R JAR and `config.yml` first.
3. If you want Landlock: place the included `webplugin-landlock` static executable at `plugins/webplugin/bin/webplugin-landlock`, set the executable bit, set `Security.Landlock.Enabled: true` and restart.
4. Confirm startup logs report `Landlock: AVAILABLE`; if your container denies Landlock, `preferred` mode warns and still runs, while `required` blocks PHP/NGINX/task launches.
5. Enable PHP and `DeploymentTasks.Enabled: true`, configure an existing application directory and one harmless one-shot task, then use the administrator commands to inspect status and logs.
6. Confirm `Settings.EnableHTML: false` leaves `HTMLPORT` unbound while PHP/NGINX remains functional.

**This beta is not yet a vetted release.** Do not run database migrations against production without backups, and do not rely on automatic startup ordering between migrations and workers.

### Example sandbox helper build (on a Linux machine with a compiler)

```sh
mkdir -p plugins/webplugin/bin
cc -std=gnu11 -O2 -Wall -Wextra native/webplugin-landlock.c -o plugins/webplugin/bin/webplugin-landlock
chmod 0755 plugins/webplugin/bin/webplugin-landlock
plugins/webplugin/bin/webplugin-landlock --probe
```

## Security boundaries

- `ProcessBuilder` avoids shell token interpretation but is **not** a sandbox. The configured PHP scripts execute with the Minecraft process's Unix user and may access its resources if Landlock is disabled/unavailable.
- The example default filesystem rules prioritize compatibility, not full process/network isolation. Landlock is not a container; it does not by itself isolate TCP destinations, environment secrets, or existing inherited file descriptors.
- If a website root or task working directory is `/home/container`, isolation of Minecraft files is ineffective. Reject or prominently warn when the configuration grants the whole server root.
- Trusted server administrators must own the task configuration. Never expose arbitrary task arguments or a shell command executor to HTTP requests or unauthenticated users.
- `once` is **at-least-once with best-effort deduplication**, not a transactional exactly-once guarantee. Keep tasks idempotent, and use Laravel's migration tracking.
- `php artisan key:generate` must never be a recurring task: regenerating the application key may make existing encrypted data inaccessible.

## Local smoke tests

```bash
mkdir -p /tmp/webplugin-automation-classes
javac -d /tmp/webplugin-automation-classes \
  src/main/java/me/jumpwatch/webserver/automation/{LandlockSandbox,ProcessSupervisor,TaskDefinition,TaskLedger,TaskEngine}.java \
  src/test/java/me/jumpwatch/webserver/automation/{ProcessSupervisorSmokeTest,TaskEngineSmokeTest}.java
java -cp /tmp/webplugin-automation-classes me.jumpwatch.webserver.automation.ProcessSupervisorSmokeTest

cc -Wall -Wextra -O2 native/webplugin-landlock.c -o /tmp/webplugin-landlock
/tmp/webplugin-landlock --probe
```

Test commands use `sh` **only inside the dedicated test classes**, never as an API offered by the production task engine.
